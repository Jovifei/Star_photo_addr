# 火烧云空快照导致空排行 Bug 记录

## 现象

用户选择明日 `9/20` 后，火烧云排行显示“符合 ≥0 分 0 个点位”和“暂无达到 ≥0 分的地点”，页面只提示“部分数据已降级”。地图仍能显示点位，但排行数据实际不可用。

## 根因

Open-Meteo 限流或响应不足时，火烧云构建层仍生成完整的 `sites` 对象，但每个早晚窗口的 `score` 都是 `null`。API 原来只以 HTTP 200 和 `payload.sites` 存在作为成功条件，并把这份空快照写入内存/磁盘。前端收到后继续计算排行，于是把数据故障伪装成“0 个地点达到 0 分”。

## 修复

- API 以有效评分点数量作为数据可用门槛；有效数量为 0 时不写入内存或磁盘缓存。
- 空刷新结果不能覆盖已有有效快照；有有效回退时返回 `stale=true` 和明确的 `refreshError`。
- 没有有效回退时返回 `502` 可重试错误，而不是 HTTP 200 空排行。
- 前端再次检查至少一个有效火烧云评分，拒绝“HTTP 200 + 空评分”响应。
- 保留四页面日期统一格式：相对语义 + 月日 + 星期，避免用户无法判断当前选择的实际日期。

## 验证

- 火烧云路由回归：2/2 PASS。
- 火烧云纯函数/日期测试：54/54 PASS；全量 Vitest：60 个测试文件、344 项 PASS。
- ESLint、TypeScript、Next 生产构建：PASS。
- ECS 只读数据探测：2026-09-19、20、21 均返回 282 个站点、564 个有效早晚评分字段。
- 浏览器 E2E：NOT_RUN，原因是当前沙箱禁止本地测试服务器监听端口；不能将其写成 PASS。

## 防复发规则

任何专题数据必须同时验证 HTTP 状态、响应结构、有效字段数量、来源/抓取时间和 stale 状态。`HTTP 200`、非空 `sites`、降级提示或地图点位存在，都不能单独证明排行数据可用。
