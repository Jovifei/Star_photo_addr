# 逐星工作区与后续产品架构

> 当前目标：先把“星空”做完整；云海保留实验能力，晚霞只做规划，不把未完成入口放进正式导航。

## 1. 当前三个工作区

| 工作区 | 核心问题 | 默认关注 | 不承担的职责 |
| --- | --- | --- | --- |
| 今夜观测 | 今晚能不能去、哪个小时最好 | 云量、卫星观测、天气门禁、连续窗口 | 长期暗夜本底评价 |
| 暗夜选址 | 哪些地点长期更暗、值得踩点储备 | VIIRS 夜光、Bortle/SQM（安装后）、海拔、当前视野推荐 | 把视觉夜光冒充现场实测 |
| 观星计划 | 已选地点怎样比较和安排 | 多夜趋势、地点矩阵、附近 10/50/100/200 km 排行 | 道路、景区开放和现场安全保证 |

三个工作区共享地点、观测夜、天气模型和时次，但标题、默认图层与决策任务必须不同。`/sites` 继续复用同一地图引擎，避免维护第二套地图和缓存；页面会明确显示“暗夜选址 · 长期暗空基础”。

## 2. 星空、云海、晚霞的产品边界

### 星空（当前主产品）

继续投入：

- 星空连续窗口；
- 高/中/低云及卫星实况；
- 月光、天文暗夜、银河高度；
- 长期暗夜选址；
- 附近观星地点排行。

### 云海（实验能力）

现有气压层与 `cloudSeaPotential` 保留为实验模块，但不与星空分混成同一个科学结论。后续独立成工作区前，需要补齐：

- 山顶与谷地地形关系；
- 低云顶/云底不确定度；
- 风向与迎背风坡；
- 现场样本校准。

### 晚霞（规划中）

晚霞应使用独立评分和页面，不复用星空分。至少需要：

- 日落方向和地平线；
- 高云/中云覆盖与西侧开口；
- 气溶胶、能见度和降水后空气；
- 日落前后时间窗口；
- 独立实拍校准。

在上述数据和验证完成前，正式导航不新增“晚霞”，避免给用户一个空壳入口。

## 3. 自动刷新策略

参考页面采用每两小时更新的思路，重点是“服务端先刷新，用户打开即读快照”，而不是要求每位用户点击刷新。当前逐星部署配置的观星快照 Worker 默认间隔为：

```dotenv
SNAPSHOT_INTERVAL_MS=1800000
```

即 30 分钟，频率已经高于两小时。正式部署应：

1. Worker 周期生成服务器快照；
2. 浏览器优先读取缓存/快照；
3. 用户手动刷新只作为受冷却保护的补充；
4. 第三方失败时保留并明确标注 stale 数据；
5. `/healthz` 不因第三方波动而失败。

## 4. 后续实施顺序

1. 完成星空主流程的真机、阿里云出口、TLS 与性能验证；
2. 安装有许可的暗夜与行政边界数据；
3. 用现场样本校准 Bortle/SQM 和云海实验指标；
4. 再独立设计云海工作区；
5. 最后建设晚霞数据模型、页面和测试。
